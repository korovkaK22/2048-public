# Пропускна здатність вводу свайпів (2048 у monobank)

Дата: 2026-07-11. Девайс: Xiaomi (MIUI), 1080x2400, під'єднаний по adb.
Скрипт: `research/scripts/measure_swipes.py` (режими `baseline` / `persistent` / `dursweep` / `burst`).
Сирі логи: `research/raw/*.json`. Свайпи — в межах ігрової дошки (bbox з калібрування проєкту), випадкові напрямки.

## 1. Метод × швидкість

| Метод | dur, мс | Свайпів/с | мс/свайп | Прийнято грою (est) | Нотатки |
|---|---|---|---|---|---|
| Baseline: окремий `adb shell input swipe` на свайп | 100 | **4.03** | 248 | ~24/30 | як зараз у боті; +~85 мс overhead на запуск adb-клієнта |
| Персистентний shell (один `adb shell`, stdin-потік) | 100 | **6.07** | 165 | ~16/30 | швидше, але гра губить ходи без пауз |
| Персистентний shell, серія впритул (pause=0) | 50 | **8.87** | 113 | ~12/20 | стеля пайплайна вводу; гра приймає ~половину |

Overhead запуску adb-клієнта на кожну команду ≈ 248 − 165 ≈ **83 мс/свайп**. Персистентний shell його прибирає. Залишкові ~165 мс при dur=100 — це сам жест (100 мс) + спавн on-device Java-процесу `input` (~60–70 мс).

## 2. Вплив duration жесту (персистентний shell, пауза 150 мс, n=30)

| dur, мс | Свайпів/с | Прийнято (est) | Висновок |
|---|---|---|---|
| 300 | 1.94 | ~26/30 | duration сам стає вузьким місцем |
| 100 | 3.14 | ~29/30 | надійно |
| 50 | 3.75 | ~21/30 | розпізнається; просідання, ймовірно, шум оцінки |
| 20 | 4.30 | ~29/30 | **гра досі розпізнає жест як свайп** — межа не досягнута навіть на 20 мс |

## 3. Ліміт самої гри (серії по 20 свайпів, dur=50, різні паузи)

| Пауза, мс | Відправлено/с | Прийнято (est) | % прийнятих |
|---|---|---|---|
| 0 | 8.87 | ~12/20 | ~60% |
| 50 | 5.99 | ~8/20 | ~40% |
| 100 | 4.63 | ~11/20 | ~55% |
| 150 | 3.68 | ~11/20 | ~55% |
| 200 | 3.18 | ~18/20 | **~90%** |

⚠️ Обмеження методики: «прийнято» оцінено непрямо через Δscore до/після серії (score росте лише при злиттях), тому це діапазон min/max з оцінкою est — значення шумні (напр., просідання на паузі 50 — радше шум, ніж ефект). Для точних цифр потрібна per-swipe перевірка дошки через vision (див. наступні кроки).

## 4. Висновок: де вузьке місце

1. **Головний ліміт — сама гра (анімація ходу)**: при бомбардуванні без пауз гра приймає лише ~50–60% свайпів; надійні ~90% — тільки з паузою ~200 мс (≈3 ходи/с). Комбінація dur=20 + пауза 150 мс дала 4.3 св/с з ~29/30 прийнятих — найкращий надійний режим у замірах.
2. **Другий ліміт — on-device `input swipe`**: кожен виклик спавнить Java-процес (~60–70 мс). Прибирається лише низькорівневою інжекцією (scrcpy control socket / sendevent), але через п.1 це дасть мало.
3. **Третій ліміт — запуск adb-клієнта на кожну команду** (~83 мс/свайп): повністю прибирається персистентним shell.

**Рекомендована цільова частота для бота: ~4 ходи/с** (dur=20–50 мс, інтервал 150–200 мс, персистентний shell) з підтвердженням кожного ходу через vision (дошка змінилась → наступний хід; це самосинхронізація краща за фіксовану паузу).

У `src/bot2048/device/` низькорівневої інжекції нема: scrcpy запускається з `control=false` (тільки відео), minitouch/sendevent відсутні. Теоретично scrcpy control socket (`control=true` + бінарний протокол інжекції) прибрав би ~60–70 мс спавну `input` і дав ~10+ св/с по пайплайну, але стеля гри (~4–5 ходів/с) робить це другорядним.

## 5. Наступні кроки

1. **Перевести бот на персистентний `adb shell`** зі stdin-потоком команд (виграш ~83 мс/хід) — найдешевша зміна.
2. **dur=20–50 мс** замість поточних 100+ (виграш ще 50–80 мс/хід).
3. **Ходити по підтвердженню vision**, а не по таймеру: свайп → чекати зміни дошки (у проєкті вже є захоплення кадрів) → наступний свайп. Це автоматично тримає максимальний темп, який гра реально приймає.
4. (Опційно) точніший замір acceptance: per-swipe парсинг дошки замість Δscore.
5. (Опційно, низький пріоритет) scrcpy control socket — лише якщо після п.1–3 впремося у ввід, а не у гру.

## Інциденти під час замірів
