# Нюанси UI телефона і гри (com.ftband.mono, 2048)

> Сирі факти зі скріншотів (`screens/`) і спостережень користувача.
> Все, що стосується поведінки реального застосунку і телефона — сюди.

## Пристрій
- Екран: **1080×2400**.
- Пакет застосунку: **`com.ftband.mono`** (monobank, вбудована гра 2048).

## Екран гри
- Хедер: «Рахунок / Рекорд».
- Над дошкою: таймер і маскот-кіт (перекриває верх дошки — не заважає клітинкам).
- ⚠️ Таймер: **дисплей оновлюється лише при свайпі** (підтверджено користувачем) — без ходів на екрані «застигає» старий час, черговий свайп підтягує актуальний.
- ✅ Семантика таймера (3 незалежні заміри, 2026-07-10): **wall-clock від створення партії** («Так, нова гра»), тікає і без ходів. Заміри: 03:31 / 01:03 / 00:32 — усі точно збігаються з часом від старту партії. Наслідки: OCR таймера читати одразу ПІСЛЯ ходу; для timer-mode бот веде власний wall-clock від моменту «Нова гра» — він дзеркалить ігровий таймер. Чи тікає при заблокованому екрані / згорнутому застосунку — ще не перевірено (edge-cases).
- ✅ **Стеля таймера — `99:60`** (користувач, 2026-07-10): далі гра НЕ рахує, дисплей застигає на 99:60. Тобто внутрішній wall-clock має верхню межу ~99 хв; для timer-режиму/аналізу вважати 99:60 saturation-стелею, не переповненням.
- Дошка **4×4** по центру екрана.
- Внизу по центру: кнопка **«Нова гра»**; праворуч — кнопка звуку; зверху зліва — «×» (вихід з гри).

- ✅ **Авто-логін валідований наскрізь наживо (2026-07-10, ТЕМНА тема):** `screencap`=0б → `uiautomator` анкори («Уведіть ПІН-код», «З поверненням, <ім_я>!», «Забули ПІН-код?», цифри 0–9) → координати пінпаду з ЖИВОГО UI-дерева збіглися з еталонними (темна тема розкладку не зсунула) → 4 тапи ПІНу (auto-submit на 4-й цифрі) → фокус лишився `Game2028Activity`, screencap знову ненульовий, впали одразу в ту саму партію. ## Читання дошки через XML (uiautomator) — МЕРТВИЙ ШЛЯХ (перевірено 2026-07-11)
- Гіпотеза: читати плитки з дерева `uiautomator dump` замість піксельної класифікації (було б швидше й точніше). **Спростовано наживо.**
- Реальний дамп посеред активної гри = **5919 байт**, містить лише `WebView` + Compose-контейнери + обфускований кастомний в'ю **`com.a.utb0`** — і **ЖОДНОГО** вузла-плитки: дошка малюється як пікселі всередині canvas/custom-view, у дереві доступності її нема.
- Наслідок: XML/accessibility-шлях до стану дошки **неможливий** у цьому клоні. Єдиний робочий спосіб зчитування — колірна класифікація (хост vision АБО on-device APK-семплер). Не витрачати час на uiautomator для дошки — тільки для AUTH-анкорів (текст «Уведіть ПІН-код» тощо), де він працює.
- ⚠️ Під час активної гри `uiautomator dump` часто відповідає **«could not get idle state»** (анімації не дають UI «заспокоїтись») — ще одна причина не тримати його на гарячому шляху. Плюс MSYS-баг шляху (`/sdcard/ui_check.xml` → `C:/Program Files/Git/sdcard/...`) обходиться `MSYS_NO_PATHCONV=1`.

## Capture-шлях і стейт-детект — scrcpy дає хибний FATAL (наживо 2026-07-11)
- ⚠️ **`--capture scrcpy` ненадійний для стейт-детекту цієї гри.** H.264-стиснення scrcpy-стріму знижує точність піксельного board-match; коли маскот-кіт перекриває верх дошки під час анімації, match падає до ~81%. А кнопка **«Нова гра» присутня ЗАВЖДИ** внизу нормального ігрового екрана → детектор бачить «board 81% + new_game_btn», не може впевнено класифікувати, віддає `SCREEN_UNEXPECTED` → `supervisor.fatal` («no safe recovery action in state game, blind taps forbidden»). Гра при цьому ЖИВА (у прикладі: 5 пустих клітинок, Рахунок 84, дошка з макс-плиткою 16) — суто хибне спрацювання. Це вбило n-tuple live-прогін на 22-му ході.
- ✅ **Правильний live-шлях — `--capture apk`** (on-device класифікація дошки + APK `not_in_game` як liveness) АБО `--capture screencap` (lossless-кадри, board-match не просідає). Обидва обходять H.264-просідання. Саме `--capture apk` відпрацював кампанію на 8342 ходи без цього FATAL. screencap повільніший (~0.65с/кадр), але для заміру SCORE (а не швидкості) — безпечний фолбек.
- ℹ️ APK-семплер (`ai.bot2048.sampler`) для `--capture apk` має вже працювати на телефоні: `pm list packages | grep bot2048` → `ai.bot2048.sampler`, процес у `ps -A`, і абстрактний сокет `@bot2048_sampler` у `/proc/net/unix`. Раннер сам робить `adb forward` (лог `apk.forwarded` / `apk.connected`). Якщо семплер не запущено — APK-режим не під'єднається.
- ℹ️ **Екран телефона гасне посеред прогону → каскад `SCREEN_UNEXPECTED`.** WiFi-adb пристрій без живлення засинає; `svc power stayon` діє лише при зарядці. Надійний фікс перед живим прогоном: `settings put system screen_off_timeout 1800000` (30 хв) + `input keyevent KEYCODE_WAKEUP`. (Гру запускати, коли телефон на зарядці — тоді ще й `stayon` тримає.)

## Безпечна зона взаємодії
- ⚠️ Зверху можуть приходити **сповіщення** — тап/свайп біля верху екрана може відкрити сповіщення або шторку.
- Всі свайпи — у середній зоні екрана (≈ 25–75% висоти, район дошки); джитер Humanizer клампиться в цю зону.
- Тапи — тільки по каліброваних координатах кнопок («Нова гра»), жодних «дослідницьких» тапів.
- Для довгих сесій: телефон на зарядці + «Не вимикати екран під час зарядки» в параметрах розробника.

## ADB — нюанси знімання і вводу (перевірено наживо 2026-07-10)
- `exec-out screencap -p` інколи повертає **порожній файл (0 байт)** — особливо одразу після анімації переходу екранів → обовʼязковий retry (1–2 повтори з паузою ~0.3 с) у адаптері.
- `input swipe ... 60` (60 мс) стабільно реєструється грою.
- Перевірений темп: **~4.8 свайпів/с — 4/4 ходів зареєстровано**, UI/таймер/анімації встигають. Реальна стеля — оверхед виклику adb (~200 мс/команда), не гра.
- Δсуми плиток на дошці точно відповідає кількості ходів (спавни не губляться на швидкості).
- Спавни: переважно «2», зафіксована одна «4» → узгоджується з класикою 90%/10% (статистику добирає research-режим).
