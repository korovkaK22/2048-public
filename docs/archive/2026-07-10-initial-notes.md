# 🎮 Проект: Бот для гри 2048 на Android

> Конспект обговорення від 2026-07-10.
> **Мета:** бот, що грає у 2048 на телефоні (Android, через USB-кабель) і набирає якомога більше очок: скріншот екрану → аналіз дошки → вибір ходу алгоритмом → свайп.

---

## 1. Алгоритми для гри 2048

Найкращий підхід — **Expectimax**: варіант мінімаксу, де замість ворожого супротивника — випадкова поява плиток (90% — двійка, 10% — четвірка). Дерево пошуку чергує вузли "хід гравця" (max) і "поява плитки" (chance, зважена за ймовірністю).

### Евристики оцінкової функції

- 🔲 бонус за порожні клітинки
- 📐 монотонність (плитки зростають в одному напрямку, "змійкою")
- 📍 великі плитки в куті / біля краю
- 🔀 гладкість (сусідні плитки близькі за значенням)

Альтернатива expectimax: **n-tuple networks + TD-навчання** (RL) — найкращі такі агенти стабільно збирають плитку 32768, але це складніший шлях.

## 2. Теоретичні межі гри (класична дошка 4×4)

- **Максимальна плитка: 131 072 = 2¹⁷.** Здавалося б, межа 2¹⁶ (16 клітинок), але якщо остання плитка, що з'явиться, — четвірка, можна дотягнути до 2¹⁷. Уся дошка при цьому — ідеальна послідовність 131072, 65536, …, 4, 2. Плитка 2¹⁸ неможлива: треба дві плитки 131072 одночасно, а місця для побудови другої немає.
- **Максимальний рахунок: ≈ 3 932 100 – 3 932 156 очок** (~3,93 млн), ~131 038 ходів. Розбіжність залежить від кількості четвірок, що випали (вони не дають очок при появі).
- **На практиці:** 131072 без undo ніхто підтверджено не отримував. Топ-гравці та ШІ досягають **65 536** і ~800 тис. – 1,2 млн очок.

Джерела: [аналіз максимального рахунку](https://www.scribd.com/document/250597014/2048), [Quora — макс. рахунок](https://www.quora.com/Whats-the-highest-possible-score-in-the-game-2048), [Quora — макс. плитка](https://www.quora.com/Which-is-the-highest-number-that-can-be-formed-in-the-game-2048), [2048game.fun](https://2048game.fun/2048-highest-score), [2048merge.com](https://www.2048merge.com/guides/highest-tile-in-2048).

## 3. Платформа: чому Android, а не iPhone

### iPhone (розглядали, відхилили)
iOS закрита: для тапів + скріншотів через кабель на Windows потрібен **WebDriverAgent** (агент Appium): сайдлоад через Sideloadly, безкоштовний Apple ID → перепідпис кожні 7 днів, запуск через tidevice/pymobiledevice3, Developer Mode тощо. Працює, але морока.

### Android (обрано ✅)
Усе штатно, без рута і джейлбрейків:

| Задача | Інструмент | Команда / деталі |
|---|---|---|
| Дзеркало екрану | [scrcpy](https://github.com/Genymobile/scrcpy) | USB, ~35–60 fps, затримка ~50 мс |
| Скріншот | ADB | `adb exec-out screencap -p > screen.png` (~0.3–0.5 с) |
| Тап | ADB | `adb shell input tap 540 1200` |
| Свайп | ADB | `adb shell input swipe 300 800 800 800 150` |

**Налаштування (5 хв):**
1. Телефон: Налаштування → Про телефон → 7 разів тап на "Номер збірки" → увімкнути **Налагодження USB** у параметрах розробника.
2. ПК: завантажити [platform-tools](https://developer.android.com/tools/releases/platform-tools) (zip, без інсталяції); scrcpy — окремий zip (ADB в комплекті).
3. Підключити кабель → підтвердити на телефоні "Дозволити налагодження з цього ПК".
4. Перевірка: `adb devices` → телефон у списку.

**Python-бібліотеки:** `adbutils` або `uiautomator2` (скріншоти і свайпи в пару рядків); `scrcpy-client` — якщо потрібен швидкий відеопотік як numpy-кадри для OpenCV.

## 4. Архітектура бота

```
скріншот (ADB) → розпізнати дошку 4×4 (по кольорах пікселів,
OCR не потрібен) → expectimax обирає хід → adb swipe →
пауза на анімацію (~200–300 мс) → повторити
```

### Оцінка складності компонентів

| Компонент | Складність | Коментар |
|---|---|---|
| Скріншоти через ADB | 🟢 легко | 1 команда |
| Розпізнавання дошки | 🟢 легко | Кольори плиток фіксовані → піксель у центрі кожної з 16 клітинок + палітра |
| Expectimax | 🟡 середньо | Алгоритм відомий, але для глибини 4–6 потрібні оптимізації (бітборди, кешування) |
| Свайпи через ADB | 🟢 легко | `input swipe` |
| Головний цикл | 🟢 легко | + детект game over і реклами |

**Оцінка часу:** робочий прототип — за вечір; доведений бот — за вихідні.

### Підводні камені

1. **Швидкість ходів:** ADB-свайп + анімація ≈ 1–1.5 с/хід → великі рахунки (16384+) = тисячі ходів = години гри. Телефон на зарядці, у параметрах розробника — "Не вимикати екран під час зарядки".
2. **Анімації:** після свайпу чекати ~200–300 мс + перевіряти, що дошка змінилась, інакше скріншот зловить плитки "в польоті".
3. **Швидкість "мозку":** наївний Python-expectimax на глибині 5 — кілька секунд/хід. Рішення: кешування + numba, або C++ движок (nneonneo) через обгортку — тоді мілісекунди.
4. **Клони гри:** якщо додаток з рекламою/бонусами/іншою сіткою — підлаштувати розпізнавання, вміти закривати спливаючу рекламу.

### Очікуваний результат

- Глибина 3–4 (чистий Python): стабільно плитка **2048–4096**, ~30–60 тис. очок
- Глибина 6–8 (оптимізований): **8192–16384**, сотні тисяч очок; обмеження — вже час гри, а не алгоритм
