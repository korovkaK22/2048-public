# Дослідження стратегій для бота 2048 (monobank-2048)

> Дата: 2026-07-10. Автор: агент-ресьорчер. Ціль документа — вибір алгоритму прийняття рішень для гри 2048, що працює наживо на телефоні (свайпи через ADB).
>
> **Ключова особливість нашого кейсу:** вузьке місце — це НЕ обчислення, а фізична швидкість свайпу через ADB (~0.5–1.5 с/хід → максимум ~40–80 ходів/хв, тобто < 1.5 ходу/с). Навіть повільний чистий Python встигає прорахувати сильний хід швидше, ніж телефон його виконає. Це кардинально змінює компроміс «швидкість vs сила» на нашу користь: обчислення фактично «безкоштовні».

---

## TL;DR

- **Основна модель:** **expectimax з бітбордом і lookup-таблицями рядків** + евристики nneonneo з вагами, знайденими CMA-ES. Це найкращий баланс «сила / складність реалізації / нуль тренування». Досягає 2048/4096/8192 практично в 100% ігор, 16384 у ~94%, 32768 у ~36% (референс C++). У чистому Python із глибиною 3 expectimax дає ~98% досягнення 2048.
- **Стартова глибина:** адаптивна — `depth = max(3, кількість_різних_плиток − 2)`, плюс імовірнісне відсікання гілок (`cprob < 1e-4`). Оскільки телефон повільний, глибину можна сміливо піднімати до 4–6 у ендшпілі, поки бюджет на хід ≤ ~1 с.
- **План Б (сильніший, але дорожчий):** **n-tuple value-функція (TD-навчання), використана як евристика оцінки в тому самому expectimax**. Це стан SOTA (32768 у 70–80% ігор). Ваги можна натренувати за години на CPU або, ще краще, **портувати вже готові відкриті ваги** (moporgic/TDL2048, alanhyue) — тренування з нуля не обов'язкове.
- **GPU не потрібен.** Ні expectimax, ні n-tuple TD не використовують GPU (це табличні/пошукові методи). 4070 Ti тут не дає переваги.
- **Таймерний режим:** оскільки фізичний свайп — головний ліміт, оптимізуємо «прогрес за хід», а не «мс на хід». Тримати глибину такою, щоб хід рахувався за ≤ бюджет, і уникати катастрофічних ходів (глибший пошук = менше фатальних помилок).

**Головні висновки з таблиці:**
1. Expectimax з хорошими евристиками — беззаперечний робочий кінь для 2048; MCTS без домен-знань програє йому.
2. Найсильніший «класичний» варіант — expectimax з lookup-таблицями ендшпілю (macroxue), але ціна — велика складність і десятки ГБ RAM.
3. Стан SOTA за силою — гібрид n-tuple + expectimax, але виграш проти простих евристик матеріалізується тільки на дуже високих плитках (32768+), які нам, імовірно, і не потрібні у таймерному режимі.

## Конкретні стартові евристики з числовими вагами

### Варіант A — ваги nneonneo (рекомендований старт, оптимізовані CMA-ES)

Оцінка дошки = сума по всіх 4 рядках і 4 стовпцях від табличної функції рядка. Кожен рядок (16-бітний, 4 плитки по 4 біти рангу) оцінюється так (константи з `2048.cpp`):

```
SCORE_LOST_PENALTY        = 200000.0   # штраф за «мертвий» рядок (немає ходів)
SCORE_MONOTONICITY_POWER  = 4.0        # степінь для монотонності
SCORE_MONOTONICITY_WEIGHT = 47.0       # вага штрафу за немонотонність
SCORE_SUM_POWER           = 3.5        # степінь для суми значень (тиск «не роздувати» дошку)
SCORE_SUM_WEIGHT          = 11.0       # вага суми
SCORE_MERGES_WEIGHT       = 700.0      # бонус за потенційні злиття (сусідні рівні)
SCORE_EMPTY_WEIGHT        = 270.0      # бонус за порожні клітинки
```

Формула оцінки одного рядка (концептуально):
```
score_row =  SCORE_LOST_PENALTY
           + SCORE_EMPTY_WEIGHT   * empty_count
           + SCORE_MERGES_WEIGHT  * merges_count
           - SCORE_MONOTONICITY_WEIGHT * min(left_mono, right_mono)   # де mono = Σ rank^POWER по спадах
           - SCORE_SUM_WEIGHT     * Σ (rank ^ SCORE_SUM_POWER)
```
де `rank` — це log2 значення плитки (порожня = 0), `merges` рахує групи однакових сусідів, а монотонність — сума `rank^4` за напрямком, що ламає порядок.

Практична порада: у Python попередньо порахувати `row_score[65536]` (таблиця на всі можливі рядки) один раз при старті — далі оцінка дошки = 8 звернень до таблиці (4 рядки + 4 стовпці транспонованої дошки). Це і є «lookup-таблиці рядків».

**Ключова ідея ваг:** порожні клітинки (270) і злиття (700) — головні позитивні драйвери; сума (`^3.5`) карає передчасне «роздування» великих плиток; монотонність (`^4`, вага 47) жорстко карає безлад саме серед великих плиток, майже не чіпаючи дрібні. Явного «кутового» доданка немає — його роль виконує монотонність (плитки шикуються у спадний градієнт до кута/краю).

### Варіант B — ваги ov3y/ovolve (простіші, зрозуміліші для першої версії)

Оцінка всієї дошки безпосередньо (без табличного розбиття по рядках):
```
eval = 0.1  * smoothness()          # −Σ |log2(a) − log2(b)| по сусідах
     + 1.0  * monotonicity2()       # нагорода за впорядкованість рядків/стовпців
     + 2.7  * log(empty_cells)      # УВАГА: логарифм кількості порожніх
     + 1.0  * maxValue()            # log2 найбільшої плитки (додає «агресії»)
```
( Java-порт wylu/md2048 використовує близькі значення, але `monoWeight = 1.3`.)

Це слабший набір, ніж nneonneo (у ov3y бувають проблеми стабільно брати 4096), але його легше налагодити й зрозуміти першою ітерацією. Рекомендація: почати з nneonneo-ваг, а ov3y тримати як sanity-check.

### Адаптивна глибина пошуку

- **Базова формула (nneonneo):** `depth_limit = max(3, count_distinct_tiles(board) − 2)`. Тобто мінімум 3 плаї; глибше, коли на дошці багато РІЗНИХ рангів плиток (складніший ендшпіль потребує далекого прорахунку).
- **Імовірнісне відсікання:** у chance-вузлах веди кумулятивну ймовірність `cprob` (старт 1.0; на кожному спавні ділиться на к-сть порожніх × 0.9 для «2» або × 0.1 для «4»). Обрізай гілку, коли `cprob < CPROB_THRESH_BASE = 1e-4`. Це робить дерево реально адаптивним: імовірні лінії йдуть на повну глибину, малоймовірні — обрізаються рано.
- **Альтернативна евристика глибини (zhy0/c2048):** глибше, коли МЕНШЕ порожніх клітинок (мало порожніх → мало гілок спавну → можна дозволити глибину; багато порожніх → погана помилка не так дорого коштує). Обидві логіки сумісні.
- **Транспозиційна таблиця:** кешуй оцінені позиції (обмеж кеш глибиною, напр. `CACHE_DEPTH_LIMIT = 15`), використовуй запис лише якщо він порахований не менш глибоко.

**Коли перемикати глибину під наш кейс:** оскільки телефон дає бюджет ~сотні мс–1–2 с/хід, тримай `depth = max(3, distinct−2)`, але дозволь рости до 5–6 у пізній грі, доки заміряний час ходу ≤ ~1 с. Якщо конкретний хід перевищує бюджет — знижуй на 1 плай (iterative deepening з таймером).

## Розділ «Таймерний режим» (максимум рахунку за обмежений час)

**Головний факт нашого кейсу:** обмеження — це фізичний свайп ADB (~0.5–1.5 с/хід). Тобто за таймер сесії ми встигнемо лише **обмежену КІЛЬКІСТЬ ХОДІВ**, а не обмежену кількість обчислень. Компроміс «швидкість алгоритму» тут майже не діє — навіть depth 3 у чистому Python рахується швидше, ніж телефон свайпне.

Наслідки для стратегії:

1. **Оптимізуй «прогрес за хід», а не «мс на хід».** Кожен свайп коштовний за часом сесії, тож головне — щоб хід максимально просував гру (злиття, компактна дошка), а не щоб він рахувався на 50 мс швидше. Це аргумент за **глибший**, а не дрібніший пошук у межах бюджету.
2. **Мінімізуй катастрофічні ходи.** Глибший expectimax = менше ходів, що заганяють у глухий кут. Оскільки ходів обмаль, кожен «злитий» хід (game over раніше часу) дорого коштує. Depth 4–6 у ендшпілі виправданий.
3. **Рахунок vs виживання.** У 2048 рахунок = сума значень від злиттів; він майже пропорційний сумі плиток на дошці + вивільненому. Стратегія «будувати найбільшу плитку в кутку» одночасно максимізує і виживання, і рахунок — окремо «гнатися за очками» не потрібно. Якщо ж таймер жорсткий і сесія обірветься до природного game over, тоді трохи зсунь ваги в бік `merges` (більше злиттів = більше очок за хід), напр. підняти `SCORE_MERGES_WEIGHT` і трохи знизити `SUM`-штраф, щоб охочіше зливати замість «економити» позицію.
4. **Мінімізуй самі свайпи-«пустушки».** Ніколи не подавай хід, що не змінює дошку (expectimax це і так відсіє, але перевіряй на рівні контролера ADB — інакше згаяний час).
5. **Паралелізуй обчислення з фізикою.** Поки телефон виконує поточний свайп (0.5–1.5 с), фоново рахуй наступний хід за передбаченою afterstate-дошкою (спекулятивно на 2–3 найімовірніші спавни). Це «ховає» весь час обчислень за час свайпу — обчислення стають повністю безкоштовними.
6. **Про speedrun-ботів:** класичні прийоми (shallow depth 2–3, alpha-beta/одностороннє відсікання, транспозиційні таблиці, time-budgeted iterative deepening ~50–100 мс/хід, aszczepanski/2048) створені, щоб робити багато ходів/с у браузері. Нам вони НЕ актуальні як пришвидшення (телефон однаково повільніший), але патерн **iterative deepening з таймером** корисний як механізм «підбирай найглибший пошук, що вкладається в бюджет».

**Підсумок таймерного режиму:** став бюджет часу на хід (напр. 0.8–1.0 с), крути iterative deepening від depth 3 угору, поки вкладаєшся; рахуй наступний хід під час свайпу; тримай nneonneo-ваги; за потреби «фарму очок» злегка підніми вагу злиттів.

- [aszczepanski/2048](https://github.com/aszczepanski/2048) — time-budgeted expectimax (min depth 1 / max 8, ліміт ~50 мс/хід, багатопотоковість) — патерн iterative deepening з таймером.

- [alanhyue/RL-2048-with-n-tuple-network (Python)](https://github.com/alanhyue/RL-2048-with-n-tuple-network) — **референсна n-tuple TD-реалізація саме на Python**, зручна для порту ваг / плану Б.

## Фінальна чітка рекомендація

### Основна модель: Expectimax + бітборд/lookup-таблиці рядків + ваги nneonneo

**Чому саме це:**
- Не потребує тренування, GPU і зовнішніх ваг — запускається одразу.
- Реалізується в Python помірними зусиллями (бітборд у 64-бітному int, precompute-таблиця `row_score`, рекурсивний expectimax з transposition table).
- Сила з запасом покриває реальні цілі: 2048/4096/8192 практично гарантовано, 16384 у ~90%+ навіть у скромній реалізації.
- Наш повільний ADB-канал робить обчислювальну вартість неістотною — можемо дозволити глибокий пошук.

**Стартові параметри:**

| Параметр | Значення | Коментар |
|---|---|---|
| Представлення | 64-біт бітборд (16 плиток × 4 біти) | таблиці ходу+оцінки на всі 65536 рядків |
| Евристика | ваги nneonneo | EMPTY 270, MERGES 700, MONO_W 47 (^4), SUM_W 11 (^3.5), LOST 200000 |
| Базова глибина | `depth = max(3, distinct_tiles − 2)` | адаптивно до складності дошки |
| Відсікання гілок | `cprob < 1e-4` | імовірнісна адаптивна глибина |
| Стеля глибини | до 5–6 у ендшпілі | доки час ходу ≤ ~0.8–1.0 с (iterative deepening з таймером) |
| Transposition table | так, кеш до глибини ~15 | суттєве прискорення пізньої гри |
| Бюджет часу/хід | ~0.8–1.0 с | усе одно ховається за час свайпу ADB |
| Спекулятивний рахунок | рахувати наступний хід під час свайпу | обчислення стають «безкоштовними» |

**Коли перемикати глибину:** старт із формули `max(3, distinct−2)`; нарощуй +1 плай, поки заміряний час ходу вкладається в бюджет; якщо хід перевищив бюджет — зменш на 1 (класичний iterative deepening). У ранній грі (багато порожніх) глибина 3 достатня; у ендшпілі (мало порожніх, багато різних рангів) піднімай до 5–6.

### План Б (якщо основної сили не вистачить або захочемо ще вище): n-tuple value-функція як оцінка листа в тому самому expectimax

- Замінюємо ручну евристику на навчену n-tuple мережу (наприклад, канонічний 4×6-tuple або 5×6-tuple набір). Це стан SOTA і піднімає 32768 з ~36% до 70–80%.
- **Не тренуй з нуля без потреби:** спершу спробуй **портувати готові ваги** (moporgic/TDL2048, HuggingFace) або взяти Python-реалізацію alanhyue як каркас. Якщо все ж тренувати — базовий TD(0) n-tuple на CPU дає ~90% рівень (2048) за ~100k партій (десятки хвилин–години), ~97–98% за ~1M партій (~5–6 CPU-год, паралелиться по ядрах). GPU не потрібен.
- Гібрид «n-tuple як evaluate() усередині нашого expectimax» вимагає мінімальних змін архітектури щодо основної моделі — це чиста заміна функції оцінки листа, тож план Б природно надбудовується над планом А.

### Чого НЕ брати
- **Vanilla MCTS / чисті Monte Carlo rollouts** — для 2048 слабші за евристичний expectimax (vanilla MCTS ~34.7k навіть гірший за flat MC ~51.5k через об'єднання випадкових спавнів). Не варто зусиль.
- **Deep RL (DQN/CNN)** — дорожче і зазвичай гірше за n-tuple TD; єдиний підхід, де 4070 Ti була б задіяна, але результат не виправдовує складності.
- **macroxue-стиль DP-таблиці ендшпілю** — дають найвищу силу (32768 у 80%), але коштують десятки ГБ RAM і серйозної інженерії; братися лише якщо ціль — стабільно 32768+, що для таймерної сесії навряд чи потрібно.
